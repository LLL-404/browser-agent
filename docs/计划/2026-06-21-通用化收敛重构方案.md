# 通用化收敛重构方案

> 日期: 2026-06-21
> 性质: 执行计划（承接 `docs/superpowers/specs/2026-06-06-browsing-agent-redesign.md` 蓝图）
> 目标: 把已经开始的"感知-决策-执行"重构从半成品状态收口为**真正的通用浏览器 Agent**
> 状态: 待评审

## 0. 背景与核心判断

### 0.1 一个关键事实

项目里已有一份 1979 行的目标架构蓝图（`browsing-agent-redesign.md` v1.1，2026-06-06），定义了：
- BrowsingAgent 统一替代 BrowserAgent
- 感知（PagePerceiver）→ 决策（DecisionEngine）→ 执行（ExecutionEngine）循环
- BrowserController 拆分为 4 模块
- 三级决策（流程骨架 / DOM 语义推理 / 视觉推理）
- 三速模型（TURBO/NORMAL/STEALTH）
- `modes/` → `flows/` 迁移、`shared/engine/` 废弃
- CLI 统一为单一 `agent` 命令

**对照代码，这份蓝图已经实现了一半**：

| 蓝图项 | 实现状态 | 证据 |
|--------|---------|------|
| BrowserController 拆分 | ✅ 已拆 | `health_monitor.py`(631行)/`log_collector.py`(153行)/`session.py`(751行)已独立 |
| PagePerceiver 感知层 | ✅ 已建 | `core/perceiver.py`(927行) |
| DecisionEngine + LoopController | ✅ 已建 | `core/decider.py`(1042行) |
| ExecutionEngine + BehaviorSimulator + SpeedController | ✅ 已建 | `core/executor.py`(651行) |
| FlowRegistry 流程骨架 | ⚠️ 半残 | `decider.py:212` 硬编码了一份 FlowSkeleton，`flows/` 目录整包是死代码（零 import） |
| BrowsingAgent 替代 BrowserAgent | ❌ 未完成 | 两个类并存，CLI 用 `BrowsingAgent`，hunt 脚本用 `BrowserAgent` |
| CLI 统一 | ❌ 未完成 | **三个** CLI 入口并存（`browser_agent/cli`、`src/cli`、`src/camoufox_cli`） |
| scraper.py 命令式 → FlowSkeleton 驱动 | ❌ 未完成 | `modes/zhipin/scraper.py`(690行) 仍是命令式，`hunt.py`(30KB) 另起一套 |
| shared/engine/ 废弃 | ⚠️ 半成品 | 已加 `DeprecationWarning`，但未删，且 `scraping_engine.py` 仍反向 import `modes.zhipin` |
| FingerprintManager 合并到 anti_detect | ❌ 未完成 | 仍在 `shared/fingerprint_manager.py` |

### 0.2 核心判断

**不需要换框架，不需要重新设计架构。需要的是"完成已经开始的收口"。**

理由：
1. 框架选型（Playwright + Camoufox + MCP SDK）版本合理，升级框架解决不了任何问题。
2. 目标架构（感知-决策-执行）已经定义清楚且核心层已建成，病根是"新旧并存没替换完"。
3. 真正的工作量在**删除旧的、接通未接的、把命令式抓取迁到新架构**。

### 0.3 与蓝图文档的关系

蓝图文档回答"**目标架构是什么**"（what/why）。本方案回答"**从当前半成品状态如何走到目标**"（how/when）。两者互补，本方案不重复蓝图的设计论证，只聚焦执行路径。

## 1. 目标定义（"通用浏览器 Agent 完成"的验收标准）

重构完成的判据，全部满足才算done：

1. **单一 Agent 类**：只有 `BrowsingAgent`，无 `BrowserAgent`。
2. **单一 CLI 入口**：只有 `agent` 命令，旧 CLI 和 camoufox_cli 要么删除要么被其吸收。
3. **单一抓取范式**：zhipin 流程通过 `FlowSkeleton` + 感知-决策-执行循环跑通，`scraper.py` 的命令式抓取逻辑被替代（业务数据层 storage/exporter 等保留）。
4. **零死代码**：`flows/` 要么被决策引擎真正消费、要么删除；`shared/engine/` 要么删要么明确为 deprecated 外壳且无内部依赖。
5. **单一打分实现**：岗位打分只有一份 `ScoringStrategy`。
6. **工程基线**：`ruff check` 零错误、`mypy` 能跑通、`.coverage`/`.playwright*` 不在 git、测试覆盖 Agent 决策循环与 CLI。
7. **新站点可接入**：新增一个 mode（如 qcc）只需写 `FlowSkeleton` + 站点 hook，不需复制 scraper 命令式代码。

### 阶段 2：CLI 收口（三个 CLI 合一）

**目标**：实现蓝图 6.1 节"单一入口"，消除三个 CLI 并存。

> 用户已决策：旧 CLI 迁入新 CLI 后删除。

#### 现状：三个 CLI 入口

| 入口 | 位置 | 调用方式 | 命令 |
|------|------|---------|------|
| 新 CLI（官方） | `src/browser_agent/cli/main.py` | `agent` / `python -m browser_agent.cli.main` | browse/extract/interact/login/snapshot/monitor/chat/server |
| 旧 CLI | `src/cli/main.py` | `zhipin-cli.bat` | login/search/report/check/server/stats/clean/investigate/open/close/ps/page |
| camoufox CLI | `src/camoufox_cli/` | `camoufox-cli.bat` | （独立 daemon/client 工具） |

#### 核心问题

新 CLI **完全没有 `--mode` 参数**，也**从未调用** `modes.*.register_cli` / `run_cli`（这两个函数在 `modes/zhipin/__init__.py:93-156` 写了却没人调，是"白写的协议"）。这是 mode CLI 接入新 CLI 的缺失环节。

#### 具体改动

1. **接通 mode 的 CLI 注册协议**（关键缺失环节）：
   - 在 `src/browser_agent/cli/main.py` 的 `_build_parser()` 增加 `--mode` 全局参数
   - 启动时若指定 `--mode zhipin`，调用 `modes.zhipin.register_cli(subparsers)` 注入子命令
   - dispatch 时若命令属于 mode，调用 `modes.zhipin.run_cli(args)`

2. **迁移旧 CLI 的 BOSS 专属命令到 zhipin mode**：
   - 旧 CLI 的 `search`/`report`/`stats`/`investigate`/`check`（BOSS 健康检查）→ 走 `modes/zhipin/__init__.py` 的 `register_cli`/`run_cli`
   - 旧 CLI 的 `login`/`open`/`page`/`ps`/`close`/`clean`（通用浏览器工具）→ 作为通用子命令迁入新 CLI
   - 旧 CLI 的 `page` 命令含写死的 `PAGE_EXTRACT_RULES`（`src/cli/main.py:354`，含 zhipin/baidu/github/zhihu），需抽到通用层（如 `browser_agent/cli/page_rules.py`）去 zhipin 化

3. **处理 camoufox_cli 去留**（需确认）：
   - 它是独立的 daemon/client 架构（`src/camoufox_cli/daemon.py` + `client.py`），功能上与新 CLI 的 `server` 命令不重叠（一个是浏览器常驻服务，一个是 MCP 服务）
   - 选项 A：作为 `agent camoufox` 子命令吸收进新 CLI
   - 选项 B：保留为独立工具，但更新文档说明其定位
   - **建议 A**，除非它有独立的部署场景

4. **删除旧入口**：
   - 删除 `src/cli/main.py`
   - 删除 `zhipin-cli.bat`（或改为调用新 CLI 的等价命令）
   - 更新 `run_hunt.bat`、`run_search.bat` 指向新入口（或改为 `agent --mode zhipin ...`）

#### 验收
- `agent --mode zhipin search --cities "深圳" --keywords "普工"` 等价于旧 `zhipin-cli search`
- `agent --mode zhipin report`、`stats` 可用
- `grep -rn "src/cli/main\|zhipin-cli" .`（排除 .venv）无残留引用
- 只剩一个 console_script：`agent = "browser_agent.cli.main:main"`

#### 风险与回滚
- 风险：**最高风险阶段**。命令调用方式变化会破坏现有 `.bat` 工作流和用户习惯。
- 缓解：
  - 保留旧 `.bat` 作为新命令的薄包装（`zhipin-cli.bat` 内部改为 `agent --mode zhipin %*`），过渡期并存
  - 每迁移一个命令立即手动验证
- 回滚：旧 CLI 文件在 git 历史中，可恢复。

### 阶段 3：flows/ 接入决策 + shared/engine 废弃落定

**目标**：消除"两套 zhipin 实现"和"声明式引擎名不副实"。

#### 核心决策点

**子决策 3a：`flows/` 目录怎么处理？**

现状：`flows/__init__.py` 导出 `ALL_FLOWS`/`ZHIPIN_FLOWS`/`QCC_FLOWS`，但**全项目零 import**。`decider.py:212` 的 `_load_builtin_flows()` 自己硬编码了一份 FlowSkeleton，根本不读 `flows/` 包。

- 选项 A（推荐）：**让 `decider._load_builtin_flows` 改为读取 `flows.ALL_FLOWS`**，复活 `flows/` 包。把 decider 里硬编码的 FlowSkeleton 迁到 `flows/zhipin/flows.py`。这样"声明式流程模板"才真正生效，符合蓝图。
- 选项 B：**删除整个 `flows/` 目录**，承认 decider 硬编码那份就是唯一实现。更简单，但放弃了"流程模板可扩展"的架构意图。

**建议 A**，因为蓝图明确要 `flows/` 作为流程骨架的家，且阶段 4 的 scraper 迁移会大量产出 FlowSkeleton，需要 `flows/` 作为归宿。

**子决策 3b：`shared/engine/` 怎么处理？**

现状：整包已加 `DeprecationWarning`（`__init__.py:1-7`），推荐用 `decider`。但 `scraping_engine.py:55,137-139` 反向 import `modes.zhipin`（循环依赖），且 `modes/zhipin/__init__.py:115` 的 `_get_engine()` 仍被 `browse` 子命令借用。

- 决策：**阶段 4 scraper 迁移完成后，删除 `shared/engine/` 整包**。迁移过程中如需借用其 `url_builder`/`profile` 数据结构，先迁到 `flows/` 或 `modes/` 再删。
- 注意：`shared/engine/` 有较多测试（`test_scraping_engine.py`/`test_dom_reader.py`/`test_profile.py` 等共约 70 个测试），删除会损失覆盖率，需评估这些测试是否迁移为对新架构的测试。

#### 具体改动（按决策 3a-A、3b-删除）

1. 改造 `decider.py:212` `_load_builtin_flows()`：删除硬编码，改为 `from browser_agent.flows import ALL_FLOWS; [self.register(f) for f in ALL_FLOWS]`
2. 把 decider 里硬编码的 zhipin/generic FlowSkeleton 迁到 `flows/zhipin/flows.py` 和 `flows/builtin.py`
3. 验证 `flows/qcc/`（当前是死代码）能在注册后被匹配
4. （阶段 4 后）删除 `shared/engine/` 整包，迁移其测试

#### 验收
- `grep -rn "ALL_FLOWS" src/` 出现真实消费方（decider）
- `from browser_agent.flows import ALL_FLOWS` 在 decider 中生效，新增一个 FlowSkeleton 能被决策引擎自动匹配
- 决策循环对 zhipin URL 能命中 `zhipin_search` 流程

#### 风险与回滚
- 风险：FlowSkeleton 的 `condition`/`fallback` 语义在 decider 硬编码版和 flows 包版可能不一致，迁移后行为漂移。
- 缓解：迁移前对比两份 FlowSkeleton 的字段，写一个等价性测试。
- 回滚：保留 decider 硬编码版作为 fallback，逐步切换。

### 阶段 4：scraper 迁移到 FlowSkeleton 驱动（核心，最大工作量）

**目标**：兑现蓝图的"声明式抓取"承诺，让 zhipin 流程通过感知-决策-执行循环跑通，而非命令式 scraper。这是"通用浏览器 Agent"成立的关键。

> 用户已决策：升级为通用浏览器 agent（即真正让新架构成为唯一抓取范式）。

#### 现状：两套并行抓取链

| 链路 | 浏览器抽象 | 入口 | 状态 |
|------|-----------|------|------|
| scraper.py | Playwright 原生 Page | `search_jobs` 等 | 命令式，被部分代码用 |
| hunt.py | BrowserAgent 封装 | `step1_search` 等 | 命令式，实际主用 |

两者**互不调用**，且打分逻辑各写一份。新架构（感知-决策-执行）目前**完全没碰抓取业务**。

#### 当前引擎能力缺口（迁移前必须正视）

经分析，现有 `shared/engine/scraping_engine.py` 即便接通也**无法支撑 zhipin 全流程**：

| 环节 | 缺口 |
|------|------|
| 翻页 | 引擎从未调用 `profile.pagination`，每个关键词只采第一页 |
| 详情采集 | `dom_reader.scrape_detail` 存在但引擎从不调用 |
| 验证码处理 | `detect_captcha` 存在但引擎不调用，无等待解除逻辑 |
| 登录态注入 | 只有检测，无 cookie/storage 注入恢复 |
| 点击进入详情 | 架构不支持（只走 `page.goto`），zhipin 部分场景需点击弹面板 |
| 并发多城市 | scraper 的 `Semaphore(5)` 并发在引擎中未实现 |

**结论**：不能简单"把 scraper 换成引擎调用"，需要把 scraper 里的 zhipin 专属逻辑**抽离为 hook/策略**，再让感知-决策-执行循环通过 FlowSkeleton 编排它们。

#### 必须从 scraper.py 抽离的 zhipin 专属逻辑

迁移时这些必须从命令式代码中抽出，作为可注入的策略/hook：

| 逻辑 | 现位置 | 抽离为 |
|------|--------|--------|
| URL 模板（`zhipin.com/web/geek/job?...`） | `scraper.py:141` | `flows/zhipin/flows.py` 的 FlowSkeleton step |
| 城市编码 | `city_codes.get_city_code` | mode 的 `city_resolver` hook |
| 登录态判断（`LOGIN_*` 选择器） | `scraper.py:103,319` | `flows/zhipin/` 的 `is_logged_in` hook |
| 验证码检测/等待 | `scraper.py:75,91` | 反爬层的 `captcha_detector` hook |
| 列表卡片解析（`JOB_*` 选择器 + `job_detail` 正则） | `scraper.py:194` | 感知层的站点特化标注规则 |
| 详情字段解析（`DETAIL_*` 选择器） | `scraper.py:271` | 同上 |
| 翻页（`NEXT_PAGE_BUTTONS` + disabled 判断） | `scraper.py:241,255` | FlowSkeleton 的 `next_page` step + 循环 condition |
| PUA 薪资解码（`_PUA_MAP`） | `hunt.py:174` | mode 的 `salary_decoder` hook |

**保留在业务层（不进框架）**：打分、关键词策略、黑名单、房租参考、招呼语画像、storage/exporter。

#### 推荐的分层（迁移后）

```
FlowSkeleton (flows/zhipin/flows.py)      ← 声明式步骤序列
  ├─ urls: 搜索/登录/首页模板
  ├─ steps: wait→click搜索框→type→click搜索→extract→click下一页(循环)
  └─ hooks 引用 ↓

SiteHooks (flows/zhipin/hooks.py)         ← zhipin 专属回调
  ├─ is_logged_in(page)
  ├─ detect_captcha(page)
  ├─ parse_list_card(card) → NormalizedItem
  ├─ parse_detail(page)
  └─ decode_salary(text)

ScoringStrategy (modes/zhipin/scoring.py) ← 业务策略（站点无关）
BrowserAgent 循环 (core/)                 ← 通用：感知→决策→执行
```

#### 具体改动（分步）

1. **建 NormalizedItem 数据模型**：定义跨站点通用的"列表项/详情"结构，zhipin 的 parse hook 输出它。
2. **写 zhipin 的 SiteHooks**：从 scraper.py 抽出 8 类逻辑为 hook 函数。
3. **写 zhipin 的 FlowSkeleton**：用蓝图的 FlowStep 语义描述搜索→翻页→详情全流程（含 `condition="has_next_page"` 循环）。
4. **扩展决策/执行层**：补齐引擎缺口——翻页循环、详情采集 step、登录态注入、验证码等待 step。这些是**通用能力**，写入 `core/`，不写死 zhipin。
5. **端到端验证**：用 `agent --mode zhipin browse --task "搜索深圳普工"` 跑通完整流程，对比与原 scraper.py 的采集结果一致性。
6. **替换 scraper.py**：zhipin 业务入口（storage 入库、报告生成）改为调用 BrowsingAgent 循环结果，删除 scraper.py 的命令式抓取函数（`search_jobs`/`_collect_list_page`/`_scrape_detail` 等）。保留 `analyze_jobs`/`generate_report` 等纯业务函数。

#### 验收
- `agent --mode zhipin browse --task "搜索深圳普工 3 页"` 能跑通，采集结果与原 scraper 数量一致（允许字段细节差异）
- `scraper.py` 中命令式抓取函数被删除或改为薄封装调用 BrowsingAgent
- 新增一个站点（用 qcc 验证）只需写 `flows/qcc/flows.py` + hooks，不需复制 scraper 命令式代码

#### 风险与回滚
- **最高风险与工作量阶段**。zhipin 反爬（PUA 字体、验证码、登录态）细节多，迁移可能触发反爬。
- 缓解：
  - **并行运行对比**：新旧两条链路同时跑，对比采集结果，一致后才切换
  - 分关键词/分城市灰度切换，不一次性全切
  - 保留 scraper.py 在 git 历史，必要时回退
- 关键不确定性：FlowSkeleton 的 `condition` 循环语义能否覆盖 zhipin 的"翻页直到无下一页/达到上限"逻辑，需在步骤 4 验证。

## 3. 决策记录

5 个关键问题已逐一调研并定调。以下是最终决策与依据。

### Q1：camoufox_cli → ✅ 删除

**决策：整个 `src/camoufox_cli/` 删除，不吸收、不保留。**

依据（读完 `daemon.py` + `client.py` 后明确）：

1. **架构上是个旁路，与项目主线冲突**。它是独立的 HTTP 守护进程（aiohttp server + 9 个 REST 端点：status/info/navigate/eval/screenshot/click/type/scroll/shutdown），**完全绕开** `BrowserController` / `BrowsingAgent` / 感知-决策-执行循环。等于项目里平白多了第四套浏览器控制层。

2. **硬依赖 `aiohttp` 却从未声明**。`daemon.py:15` `from aiohttp import web`，但 `pyproject.toml` 和 `requirements.txt` 都没列 aiohttp。这是一个**隐藏的依赖缺失**——谁要跑 camoufox_cli 都得自己装 aiohttp。引入 `agent camoufox` 子命令会把这个未声明依赖正式化，不如砍掉。

3. **功能 100% 被新架构覆盖**。它做的事（navigate/eval/click/type/scroll/screenshot）正是 `BrowserController` 和 MCP 工具的子集，没有任何独有能力。唯一的"独有"是守护进程常驻——但 `BrowserController` 本身就支持长期持有浏览器实例，MCP server 也是常驻的。

4. **裸 except 满天飞**（`daemon.py:39`、`client.py:47,158` 等多处 `except:`），代码质量低于项目主线。

**执行**：阶段 0 直接删除 `src/camoufox_cli/` 整个目录、`camoufox-cli.bat`。若有人真用了它，等价命令是 `agent browse <url>` 或直接调 MCP。

### Q2：FlowSkeleton 存储格式 → ✅ Python 代码

**决策：流程骨架用 Python dataclass 定义（`FlowSkeleton`/`FlowStep`），YAML 仅作为后续可选的加载格式。**

依据：
- 与蓝图 9.1 节倾向一致。
- Python 代码有类型安全 + IDE 补全 + 重构支持，zhipin 流程复杂（含 condition 循环/fallback），YAML 表达这些语义容易出错。
- 流程骨架主要由开发者编写（接入新站点时），不是给最终用户编辑的。
- `decider.py` 现有的 `FlowSkeleton` 已经是 dataclass（阶段 3 只是把它从硬编码迁到 `flows/` 包，格式不变）。

YAML 加载作为**阶段 4 之后的可选增强**，本次不做。

### Q3：shared/engine 测试迁移 → ✅ 分类处理，不整体保留

**决策：按测试意图分类——测"数据结构正确性"的迁移，测"声明式引擎特有行为"的删除。**

具体：
- `test_profile.py`(22)、`test_filter_chain.py`(17)、`test_url_builder.py`(8) → **迁移**。这些测的是 `SiteProfile`/过滤规则/URL 构建的数据契约，新架构的 `FlowSkeleton` + 站点 hook 仍需要等价物，迁移为对新数据结构的测试。
- `test_scraping_engine.py`(19)、`test_dom_reader.py`(19) → **删除**。这些测的是声明式引擎的特定编排（卡片采集单页流程），新架构用感知-决策-执行循环替代，行为模型不同，迁移成本 > 重写成本。
- `test_adapter.py`(15)、`test_report_builder.py`(10) → **评估后定**。若 `ScoringStrategy`（阶段 5）和报告生成保留相似接口，则迁移。

净影响：约 70 个测试 → 保留约 45-55 个（迁移后改写），损失约 15-25 个低价值测试。`fail_under` 在阶段 3 短暂下降，阶段 6 补回。

### Q4：hunt.py → ✅ 删除，能力分别收编

**决策：删除 hunt.py，把它的能力拆解后分别并入框架和 mode。**

依据（读完 hunt.py + `run_hunt.bat` 后明确）：

hunt.py 是 30KB 的"一条龙"脚本，包含四类能力，分类归宿如下：

| hunt.py 的能力 | 归宿 |
|----------------|------|
| 多城市×多关键词调度 + 断点续传（`cities_done`，hunt.py:410/527） | **提升为框架通用能力**：FlowSkeleton 支持多城市循环 step，或作为 `BrowsingAgent.run_multi_city()` 方法 |
| 搜索抓取（内联 JS 抽取卡片、活跃度正则、僵尸过滤） | **被阶段 4 取代**：FlowSkeleton + 感知层标注替代内联 JS |
| 岗位打分（`_score` hunt.py:275） | **并入** `modes/zhipin/scoring.py` 的 `ScoringStrategy`（阶段 5） |
| 企查查背调（`step2_qcc_verify`）+ 国家企业信用网背调（`step2_gov_verify`） | **保留为** `modes/zhipin/verify.py`（招聘业务专属，通用框架不碰） |
| PUA 薪资解码（`_PUA_MAP` hunt.py:174） | **并入** zhipin 的 `salary_decoder` hook（阶段 4） |
| 报告生成（`report` hunt.py:356） | **并入** `modes/zhipin/report.py`，复用 `ScoringStrategy` |

`run_hunt.bat` 的"一条龙"工作流改为：`agent --mode zhipin hunt --cities "..." --keywords "..."`（阶段 2 接通 mode CLI 后），内部按 step 调用上述各模块。

**为什么不留作示例脚本**：它内嵌了太多本该分离的关注点（搜索+打分+背调+报告+PUA解码混在一个文件），留作示例反而传播坏模式。背调逻辑单独抽成 `verify.py` 更清晰。

### Q5：执行节奏 → ✅ 间歇交付，里程碑制

**决策：按里程碑间歇交付，每个里程碑 review 后再继续。不连续跑完。**

三个里程碑：

| 里程碑 | 含阶段 | 工作量 | 风险 | 行为变化 | review 关注点 |
|--------|--------|--------|------|---------|--------------|
| **M1：清理收口** | 阶段 0+1+2 | 约 2 天 | 低-中 | 命令调用方式变（.bat 适配），抓取行为不变 | 三 CLI 是否真合一；旧命令等价性 |
| **M2：架构落定** | 阶段 3+4 | 约 3-4 天 | 高 | 抓取内部重构，结果应等价 | FlowSkeleton 能否跑通 zhipin 全流程；新旧采集结果对比 |
| **M3：质量收尾** | 阶段 5+6 | 约 1.5-2 天 | 中 | 打分可能微变 | 打分等价性；测试覆盖；文档一致 |

**强制门禁**：M2 必须等 M1 review 通过且 `pytest` 全绿才启动；M3 必须等 M2 的新旧采集对比测试通过才启动。任何里程碑失败可停在当前状态，项目仍可用。

特别说明 M1 的 `pytest` 全绿门槛——当前 mypy 跑不起来、ruff 143 错误，阶段 0 必须先把这些修到基线，否则后续每个阶段都会被噪声淹没。
